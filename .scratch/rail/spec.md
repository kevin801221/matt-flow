# 軌道：讓 Claude 沿著 Matt 的流程走

## Problem Statement

matt-flow 現在是一個給人看的面板：列出步驟、按鈕可以把指令填進輸入框。但真正會跳步驟的是 Claude，而面板完全約束不了它：

- Claude 不知道流程走到哪一步，會自己建議流程以外的下一步（例如面板說 `/grill-with-docs`，Claude 的 recap 卻說 `/to-spec`），兩邊各說各話。
- 規格還沒寫、問題還沒問清楚，Claude 照樣可以直接改程式碼、commit，沒有任何東西擋它。
- 自動偵測「跑完了哪個 skill」用的 `skill.prompt` 事件，被 Claude Code 內建的安全 hook 跳過，所以跑完 skill 後面板不會自動前進，也不會預填下一步。
- 「通過」的判斷是「skill 開始跑了」，所以 `/to-spec` 才剛輸入、規格根本沒寫出來，面板就已經打勾。

結果是使用者得自己記流程、自己輸入指令、自己盯著 Claude 不要跳步，面板只是一張清單。

## Solution

把 matt-flow 改成約束 Claude 的軌道，人只需要在交棒時按 Enter：

- matt-flow 把目前的功能、等級、步驟，以及哪些動作會被擋下，寫進 Claude 的系統提示，讓 Claude 知道自己在流程的哪裡，並遵守交棒的規矩。
- Claude 想在步驟還沒通過時改程式碼或 commit，動作會被擋下；擋下訊息會說明還差哪一步、該由人輸入哪個指令，同時把那個指令預填進輸入框。
- 步驟通過時，Claude 停下來交棒，matt-flow 把下一步的指令預填進輸入框，由人按 Enter 啟動。
- 有產出物的步驟，看產出物在不在來判斷通過；沒有產出物的，看 skill 有沒有跑過。
- 人永遠可以跳過一個步驟、結束一個功能，或在某個專案關掉整個軌道。
- 面板退居儀表板：顯示進度，提供跳過和「我卡住了」。

## User Stories

1. 身為使用者，我希望 Claude 知道目前的功能走到哪個步驟，這樣它的建議才會跟面板一致，不會互相矛盾。
2. 身為使用者，我希望步驟通過時 Claude 會停下來告訴我下一步的指令，這樣什麼時候往下走由我決定。
3. 身為使用者，我希望每次交棒時下一步的指令都已經預填在輸入框，這樣我只要按 Enter，不用記指令也不用打字。
4. 身為使用者，我希望沒有進行中的功能時，Claude 改程式碼會被擋下，這樣每一次修改都從想清楚開始。
5. 身為使用者，我希望擋下訊息寫明哪個指令可以解鎖，這樣我清楚知道下一步要做什麼。
6. 身為使用者，我希望 Claude 被擋下時，解鎖用的指令已經預填好，這樣恢復只要按一個鍵。
7. 身為使用者，我希望程式碼要等我輸入 `/implement`（高手等級是 `/implement-spec`）之後才解鎖，這樣「想清楚了」是由我決定，而不是 Claude。
8. 身為使用者，我希望 Claude 自己呼叫 `tdd` 不會解鎖程式碼，這樣 Claude 沒辦法自己越過交棒。
9. 身為使用者，我希望程式碼被鎖住時，Claude 還是能寫詞彙表、ADR、規格和任務卡，這樣思考類的步驟才能留下產出物。
10. 身為新手或進階等級的使用者，我希望這次動手做還沒跑過 code-review 之前，`git commit` 會被擋下，這樣沒有 review 過的東西不會被 commit。
11. 身為使用者，我希望 code-review 之後的修正不用再 review 一次就能 commit，這樣 review 的成本不會失控。
12. 身為高手等級的使用者，我希望並行分身的 commit 不會被擋下，這樣 `/implement-spec` 能照 Matt 的設計運作。
13. 身為使用者，我希望「寫成規格書」要等規格真的存在才算通過，這樣面板不會替沒有產出的步驟打勾。
14. 身為使用者，我希望「切成任務卡」要等任務卡檔案真的存在才算通過，這樣進階和高手不會在沒有任務卡的情況下進入動手做。
15. 身為使用 GitHub 或 GitLab tracker 的使用者，我希望步驟在 skill 跑過之後就算通過，這樣沒有本地檔案也能使用軌道。
16. 身為使用者，我希望跑了任何一個流程步驟的 skill 就自動開始一個功能，這樣我不用另外宣告。
17. 身為使用者，我希望功能在 `/retro` 之後，或我手動結束時就結束，這樣下一個功能會從「把想法問清楚」重新開始。
18. 身為使用者，我希望跳步輸入 `/implement` 時指令照常執行、只跳出提醒，這樣我自己的決定永遠不會被擋。
19. 身為使用者，我希望被我跳過的步驟記為「跳過」，這樣進度顯示的是實際做了什麼。
20. 身為使用者，我希望能用 `/matt-flow skip` 或面板按鈕跳過目前的步驟，這樣小修改不用走完整個流程。
21. 身為使用者，我希望 `/matt-flow end` 可以結束目前的功能，這樣我能明確地放棄或收尾。
22. 身為使用者，我希望能用 `/matt-flow off` 和 `/matt-flow on` 在單一專案關閉或開啟軌道，這樣不走這套流程的專案不會被打擾。
23. 身為使用者，我希望沒跑過 `/setup-matt-pocock-skills` 的專案裡軌道完全安靜，這樣 matt-flow 不會在別的地方礙事。
24. 身為使用者，我希望只輸入 `/matt-flow` 時還是開關面板，這樣原本的習慣不用改。
25. 身為使用者，我希望面板顯示功能的進度、目前的步驟、哪些步驟被跳過，以及 context 用量，這樣我一眼就知道自己在哪裡。
26. 身為使用者，我希望面板上的「我卡住了」按鈕照樣把我的狀況預填成 `/ask-matt`，這樣卡住時有地方求助。
27. 身為使用者，我希望隨時可以換等級，這樣一個功能要走多少流程由我決定。
28. 身為使用者，我希望狀態列繼續顯示下一步的指令，這樣不用打開面板也看得到。
29. 身為使用者，我希望改版前存的進度能延續下來，這樣升級不會把我的專案進度清掉。
30. 身為 Claude，我希望系統提示寫明現在哪些動作會被擋，這樣我不會去嘗試、白白浪費一輪。
31. 身為 Claude，我希望擋下訊息告訴我要停下來交棒，而不是想辦法繞過，這樣我不會改用 Bash 寫檔。
32. 身為 Claude，我希望我透過 Skill 工具執行的 skill 在允許的範圍內也算數，這樣 `/implement` 自己跑的 code-review 才能解鎖 commit。
33. 身為 Matt skills repo 的維護者，我希望 em dash 防護和同步提醒照舊運作，這樣這次改版不會破壞那個 repo 的規則。

## Implementation Decisions

- **只有一個模組。** 所有行為都留在現有的 hooks 模組裡，不新增模組。面板、狀態列、指令和每個關卡，都讀同一份「每個專案各一份」的狀態。
- **偵測 skill 執行。** `skill.prompt` 不能用：Claude Code 的組織層級安全 hook 刻意在這個事件上跳過使用者層級的 plugin。改成兩個來源：人輸入指令時，從 `prompt.submit` 的 command 名稱取得；模型透過 Skill 工具執行且呼叫成功時，從 `tool.call`（Skill）取得。plugin 的 skill 名稱帶有前綴（`mattpocock-skills:to-spec`），比對前先去掉。這個修正已經在工作目錄裡，還沒 commit。
- **誰啟動的有差。** 人輸入和模型執行的 skill 都可以讓步驟通過，只有一個例外：「動手做」只有在人輸入 `/implement` 或 `/implement-spec` 時才通過。模型自己執行 `tdd` 永遠不會解鎖程式碼。
- **每個專案的狀態**，跨 session 保存，以專案的工作目錄為鍵：等級；是否有進行中的功能，以及規格產生後的功能名稱；每個步驟的狀態（未通過 / 通過 / 跳過）；這個功能是否已經開始動手做；動手做開始後是否跑過 code-review；這個專案是否關掉了軌道；已完成的功能數。
- **舊進度的轉換。** 現有版本存的進度（已完成步驟的清單和輪數），載入時分別轉成「已通過的步驟」和「已完成的功能數」。使用者存過的東西一律不丟。
- **通過的規則。**
  - 設定專案：`/setup-matt-pocock-skills` 寫的 tracker 設定檔存在（跟現在一樣）。
  - 寫成規格書：使用本地 markdown tracker 時，依 tracker 的慣例，某個功能資料夾裡有規格檔；其他 tracker 看 skill 有沒有跑過。
  - 切成任務卡：使用本地 markdown tracker 時，某個功能資料夾裡至少有一個任務卡檔案；其他 tracker 看 skill 有沒有跑過。
  - 動手做：人輸入了 `/implement` 或 `/implement-spec`。
  - 把想法問清楚、檢查、開 PR、複盤：skill 有跑過。
  - 用的是哪種 tracker，從 tracker 設定檔的標題判斷。
  - 產出物的檢查在每一輪結束時進行，跟現在檢查 setup 的時機一樣。
- **功能的生命週期。** 沒有進行中的功能時，任何流程步驟的 skill（setup 除外）一跑就開始一個功能。「複盤」通過，或人執行 `/matt-flow end`，功能就結束：已完成的功能數加一，setup 以外的步驟全部重設。
- **什麼算程式碼。** 專案內不是 markdown、也不在 tracker 暫存資料夾或 docs 資料夾底下的檔案。專案外的檔案一律不管。
- **程式碼關卡。** 專案做過 setup、軌道開著，而且進行中的功能還沒開始動手做時，對程式碼的 Edit、Write、NotebookEdit 一律擋下。擋下訊息寫明目前的步驟，以及解鎖要用的指令：沒有進行中的功能時是 `/grill-with-docs`，否則是通往動手做路上下一個還沒通過的步驟。訊息也要求 Claude 停下來交棒，並且不准改用 Bash 寫檔。同一個指令會預填給人。
- **commit 關卡。** 新手和進階等級，在動手做期間、還沒跑過 code-review 時，執行 `git commit` 的 Bash 呼叫會被擋下。動手做以外的時間 Claude 根本改不了程式碼，所以那時候的 commit 只可能是文件，一律放行。高手等級的 commit 永遠不擋。
- **人輸入的指令永遠不擋。** 人輸入某個步驟的指令，而等級裡更前面的步驟還沒通過時，指令照常執行，跳出提示說明哪些步驟被視為跳過，並把它們記為「跳過」。
- **交棒。** 步驟通過時，在這一輪結束時預填下一步的指令（沿用現有的預填機制），並跳出提示說明下一步。matt-flow 自己絕不執行任何步驟的指令。
- **系統提示。** 在做過 setup、軌道開著的專案裡，於系統提示最後加一段（session 範圍），內容包括：功能和它的名稱（如果已經有）、等級、目前的步驟、現在哪些動作會被擋以及各自的解鎖指令，還有規矩：每次交棒都要停下來把下一步的指令告訴人；除了下一步的指令，不要建議其他流程指令；絕不繞過任何阻擋，包括透過 Bash。
- **指令。** 只輸入 `/matt-flow` 時開關面板。參數：`skip` 把目前的步驟記為跳過；`end` 結束功能；`off` 和 `on` 在這個專案關閉或開啟軌道。每個參數都回一行訊息，說明改了什麼、下一步是什麼。
- **面板**改成儀表板：等級按鈕；進度，跳過的步驟要有明顯的區別；目前步驟的卡片，上面有「跳過」和「我卡住了」；context 用量；已完成的功能數。拿掉「填入指令」和「做完了」。「第 N 輪」改用詞彙表的說法，顯示功能數。
- **不動的部分。** Matt skills repo 裡的 em dash 防護和同步提醒；狀態列的文字格式；context 用量計。
- **版本。** manifest 的版本升到 0.3.0，已安裝的副本才會更新。

## Testing Decisions

- **只有一個切面：整個 hooks 模組，透過 `claude plugin test`，用 Claude Code 驅動它的方式來驅動。** 測試發出引擎事件（人輸入指令、模型呼叫 Edit / Write / Bash / Skill、一輪結束、組合系統提示、畫面板、按按鈕），只檢查從外部看得到的結果：呼叫有沒有被擋、擋下訊息寫了什麼、系統提示加了哪些段落、面板上的文字、預填了什麼、跳出哪些提示。
- **假引擎**底下加一個每個測試各自設定的假檔案系統：每個測試自己指定哪些檔案存在、某個資料夾列出什麼，取代現在「所有檔案都存在」的假設。這只是測試輔助，不是新的切面。
- **好的測試**對應使用者故事裡的一個行為，那個行為壞掉時測試就會失敗；絕不直接讀模組內部的狀態或私有函式。
- **既有範例：** 現有的測試已經是這樣驅動模組的：底下一個假引擎、`session.start`、一個透過 `prompt.submit` 輸入指令的輔助函式、對 Edit 和 Skill 的 `tool.call`，以及用 `ui.mount` / `press` 操作面板。em dash 的測試就是驗證擋下結果的範本。
- **要涵蓋的範圍：** 程式碼關卡在「沒有功能」「還沒動手做」「輸入 `/implement` 之後」三種情況；`tdd` 不會解鎖；commit 關卡在各等級的行為，以及跑過 code-review 之後解除；文件和暫存資料夾的檔案永遠不擋；本地 tracker 上規格和任務卡靠產出物通過，GitHub tracker 上靠 skill 跑過通過；跳步的指令被記為跳過；`/matt-flow` 的每個參數；系統提示只在做過 setup 而且開著時出現；舊進度能載入；em dash 防護不變；面板在每種介面上都正常。

## Out of Scope

- 開 PR 的關卡。
- 用程式硬擋透過 Bash 寫檔；改由擋下訊息和系統提示禁止（已知漏洞）。
- 擋下人輸入的指令。
- 替人執行任何步驟的指令，包括會直接執行指令的面板按鈕。
- 高手等級的 commit 關卡；那裡的 review 由 `/implement-spec` 自己的最後一步負責。
- 在 GitHub 或 GitLab tracker 上用產出物判斷規格和任務卡。
- 在乾淨環境驗證 README 的安裝方式；這是改版上線後另外要做的檢查。

## Further Notes

- Matt 流程裡大部分的 skill 都設了 `disable-model-invocation`，所以就算 Claude 想，也沒辦法自己越過交棒；軌道依靠這一點，再補上 Claude 碰得到的那些關卡。
- 「把想法問清楚」在 skill 開始時就算通過，而不是結束時。這是可以接受的：程式碼要等人輸入 `/implement` 才解鎖，所以這個落差沒辦法被拿來提早寫程式。
- commit 關卡每次動手做只要求跑一次 code-review，不是每次修改後都要；review 之後的修正算在那次 review 裡。
- 第一次的「乾淨環境」測試其實沒有在乾淨的設定目錄裡執行，所以 README 的 marketplace 安裝方式仍然沒驗證過。
- 實作前先載入 `plugin-authoring` skill，查 hooks 的 API 和規則。已經踩過的坑：接收 `$` 的函式必須宣告在檔案最上層，寫在 `register` 裡面的話，模組會載入失敗。
- 這個 repo 的 mod 是從個人層級的 skills 資料夾直接載入的，存檔後會立刻重新載入到所有開著的 session。存了一個載入不了的版本時，session 會顯示 `reload failed` 並保留上一個能用的版本；但能載入、行為卻錯了的版本，會直接生效。
